# ElementX production setup guide

ElementX v1 is **one Vite/React frontend** (`frontend/elementx-frontend`) + **one FastAPI backend**
(`backend`) + **MongoDB** for accounts + a **SQLite database and original-file directory on one persistent
disk** for research data.

This guide covers staging and production on Render. Nothing here is applied automatically: you create or
sync the services yourself. Items that depend on your Render plan are marked **VERIFY** – they were not (and
cannot be) confirmed from the repository.

## 1. Architecture

```
Browser ──https──> elementx-frontend (Render static site, Vite build, VITE_API_URL baked in)
   │
   └──https + Bearer JWT──> elementx-backend (Render web service, Python 3.11, 1 instance, 1 worker)
                                 ├── MongoDB Atlas          (accounts / identity)      MONGODB_URI
                                 └── persistent disk /var/data
                                       ├── elementx.db     (SQLite, WAL)              DATABASE_URL
                                       └── experiments/<uuid>/original.<ext>          DATA_DIR
```

Design constraints that follow from this:

* **Single instance, single worker.** SQLite supports one writer process. `numInstances: 1`, `--workers 1`;
  the backend refuses to start if `WEB_CONCURRENCY` is set to anything but 1. Do not scale horizontally.
* **Disk required.** In production the backend refuses to start unless `DATA_DIR` is an absolute path that is
  a **mounted volume**, and `DATABASE_URL` is a SQLite file *inside* `DATA_DIR`. A service without its disk
  fails to boot instead of silently writing to ephemeral storage that would vanish on the next deploy.
* Deploys of a service with a disk restart the single instance (brief downtime). Plan deploys accordingly.

## 2. Environment variables

Set secrets in the Render dashboard (never in Git, chat, or the frontend). The repository's `render.yaml`
lists every key; `sync: false` keys are prompted for.

### Backend (`elementx-backend`)

| Variable | Required | Purpose / rules |
| --- | --- | --- |
| `ELEMENTX_ENV` | **yes** (`production`) | Turns on the fail-fast checks below. Without it the app runs in *development* mode (permissive CORS, in-memory accounts, demo bootstrap). |
| `JWT_SECRET` | **yes** | ≥ 32 random characters; placeholder/known-default values are rejected. Generated by `render.yaml` (`generateValue`). Rotating it signs everyone out. |
| `MONGODB_URI` | **yes** | `mongodb://` or `mongodb+srv://`. No in-memory fallback in production; the service aborts at startup if MongoDB is unreachable. |
| `DATA_DIR` | **yes** | `/var/data` – absolute, writable, a mounted persistent disk. |
| `DATABASE_URL` | **yes** | `sqlite:////var/data/elementx.db` – absolute SQLite file inside `DATA_DIR`. PostgreSQL is not supported in v1. |
| `CORS_ORIGINS` | **yes** | Exact frontend origin(s), comma-separated, e.g. `https://elementx-frontend.onrender.com`. No wildcard, no paths. Credentials are never allowed cross-origin (the app uses a bearer token). |
| `MP_API_KEY` | for Materials Project | Without it formula lookups return 503; `/health` shows `materials_project_configured: false`. |
| `GEMINI_API_KEY` / `GOOGLE_API_KEY` | optional | Physics Copilot LLM. Without any provider the Copilot answers from stored records only (and says so). |
| `GEMINI_MODEL` | optional | Default `gemini-2.5-flash`. |
| `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` | optional | OpenAI fallback provider. |
| `MAX_UPLOAD_MB` | optional (50) | Magnetometry/XRD upload limit → HTTP 413. |
| `MAX_CIF_UPLOAD_MB` | optional (5) | CIF upload limit. |
| `SQLITE_BUSY_TIMEOUT_MS` | optional (10000) | How long a writer waits for the SQLite lock. |
| `PYTHON_VERSION` | Render | `3.11.x` (**VERIFY** the exact patch version is offered). The app and dependency set are tested on 3.11. |
| `ELEMENTX_ALLOW_UNMOUNTED_DATA_DIR` | **do not set on Render** | Escape hatch that disables the mounted-volume check. Only for a self-managed host whose `DATA_DIR` you know is durable. |
| `WEB_CONCURRENCY` | leave unset | Must be 1 if present. |

Not available in production: `ELEMENTX_ENABLE_DEMO` (removed – the shared demo account bootstrap is always disabled
in production).

### Frontend (`elementx-frontend`)

| Variable | Required | Purpose / rules |
| --- | --- | --- |
| `VITE_API_URL` | **yes** | Public `https://` URL of the backend, no trailing slash. Baked into the bundle **at build time** – change it and redeploy the frontend. The build fails if it is missing, not https, or contains credentials. |
| `NODE_VERSION` | Render | `22.12.0` (Vite 7 needs Node `^20.19.0 || >=22.12.0`). **VERIFY** it is offered. |

**Never** create a `VITE_*` variable holding a secret – everything prefixed `VITE_` is published in the JavaScript
bundle. The production build refuses secret-looking `VITE_*` names, and a post-build scan fails the build if the
bundle contains a known secret value or credential pattern.

## 3. What the backend enforces in production

On start (before serving traffic) with `ELEMENTX_ENV=production` the app exits with a clear message – naming the
problem, never the value – if any of these is wrong: missing/weak/default `JWT_SECRET`; missing/placeholder
`MONGODB_URI`; `DATA_DIR` missing, relative, not writable, or **not a mounted volume**; `DATABASE_URL` not an
absolute SQLite file inside `DATA_DIR`; `CORS_ORIGINS` missing, wildcard, or not bare origins;
`WEB_CONCURRENCY` ≠ 1. It also aborts if MongoDB cannot be reached or the research database cannot be opened.

At runtime in production:

* Every route requires a valid JWT, except `/health`, `/`, register and login. This includes the stateless
  scientific endpoints (`/api/query-formula`, `/api/analyze-magnet`, `/api/parse-cif`,
  `/api/magnetometry/analyze`), which would otherwise let anonymous users spend Materials Project quota and CPU.
  (In development they stay open so scripts and tests keep working.)
* Research data is owner-scoped; other users' samples/experiments return `404`.
* `/docs`, `/redoc`, and `/openapi.json` are disabled.
* `/api/demo/bootstrap` returns `404` and cannot create or reset the shared demo account. The publicly
  documented demo login (`demo@elementx.dev`) is also **rejected at login/registration** even if that account
  already exists in MongoDB, so a pre-existing shared account cannot be used to reach the research workspace.
  Use a **fresh MongoDB database for staging**; before cutting production over to an existing database, remove or
  rotate that account's password there yourself (this repository never deletes accounts).
* Upload limits apply; error responses are generic (details are logged server-side only).

## 4. First-time staging setup (Render dashboard)

1. **Confirm your Render plan supports a persistent disk** for a web service (and the disk size/price you accept).
   If it does not, stop – production on ephemeral storage is not supported.
2. **MongoDB:** create a MongoDB Atlas cluster/database user for ElementX; allow Render's outbound IPs (or Atlas's
   documented access method); copy the connection string. Enable Atlas backups.
3. **Create the services** from the repository: *New → Blueprint*, pick the branch you intend to deploy
   (do this for a **staging** copy first), review the plan shown for `elementx-backend`, and enter the prompted
   values (`MONGODB_URI`, `MP_API_KEY`, optionally `GEMINI_API_KEY`). Leave `CORS_ORIGINS` and `VITE_API_URL`
   empty for now if the URLs are not known yet. Do not delete or rename any existing Render resources you rely on;
   the Blueprint reuses the names `elementx-backend` and `elementx-frontend` – check what the dashboard says it
   will create vs. update before applying.
4. After the first backend deploy note its URL (`https://<backend>.onrender.com`); after the frontend deploy note
   its URL. Then set:
   * backend `CORS_ORIGINS` = the frontend origin (exact scheme + host, no trailing slash) → redeploy backend;
   * frontend `VITE_API_URL` = the backend URL → redeploy frontend (it is a build-time value).
5. Check `https://<backend>/health`: `status: ok`, `researchStorage: true`, `mongodb: true`,
   `materials_project_configured: true`.
6. Run the smoke test in §6, then take and verify a first backup (`docs/BACKUP_AND_RECOVERY.md`).

## 5. Deploying a new version

1. Take and verify a backup (copy it off the server).
2. Deploy backend, then frontend (both have `autoDeploy: false`; trigger from the dashboard).
3. Smoke test (§6).

### Rollback

* **Backend:** redeploy the previous commit from the Render dashboard. The schema upgrade is additive and
  idempotent, so an older backend can still read the database; if data was damaged, restore from the backup
  taken in step 1.
* **Frontend:** redeploy the previous commit. To fall back to the legacy Create React App build, point a static
  site at `frontend/` with the settings in `frontend/render.yaml` (kept as a rollback reference). The CRA app is
  *not* part of v1 and still shows legacy, unreviewed magnetics/XRD views.

## 6. Smoke test (after every deploy)

1. `GET /health` → `ok`, `researchStorage: true`, `mongodb: true`.
2. `GET /docs` → 404 (docs disabled).
3. `POST /api/parse-cif` without a token → 401.
4. Register/sign in in the Vite app; create a sample; upload a magnetometry `.dat` and an XRD file; reopen both.
5. Sign in as a second user: the first user's sample is not visible.
6. Physics Copilot answers from stored values (with an LLM key set, the badge/meta shows the provider).
7. Materials / CIF: a formula lookup and a CIF parse work.
8. Redeploy the backend and confirm the saved experiments are still there (proves the disk persists).

## 7. Local production-mode rehearsal

```bash
cd backend
mkdir -p /tmp/elementx-prod/data
ELEMENTX_ENV=production \
JWT_SECRET="$(openssl rand -hex 32)" \
MONGODB_URI='mongodb://localhost:27017/elementx' \
DATA_DIR=/tmp/elementx-prod/data \
DATABASE_URL=sqlite:////tmp/elementx-prod/data/elementx.db \
CORS_ORIGINS=http://localhost:5173 \
ELEMENTX_ALLOW_UNMOUNTED_DATA_DIR=true \
./venv/bin/python3 -m uvicorn main:app --port 8000
```

(`ELEMENTX_ALLOW_UNMOUNTED_DATA_DIR` is needed locally only because a temp directory is not a mounted volume; it
also requires a reachable MongoDB.)

## 8. Dependency policy

`backend/requirements.txt` states direct dependencies with compatible ranges;
`backend/constraints.txt` pins the full verified set (Python 3.11) and is used by the Render build and the
Dockerfile (`pip install -r requirements.txt -c constraints.txt`). Do **not** upgrade the scientific stack
(`numpy`, `scipy`, `pymatgen`, `mp-api`, `emmet-core`) blindly: `mp-api 0.45.x` is incompatible with
`emmet-core ≥ 0.87` (requirements cap it at `<0.87`). To refresh the pins deliberately: create a clean 3.11
virtualenv, `pip install -r requirements.txt`, run the full backend suite and a live Materials Project lookup,
then `pip freeze` into `constraints.txt`.

## 9. Known limits (v1)

* No rate limiting on login/registration or the stateless endpoints (authentication only).
* No automated off-site backups, and no raw-file download endpoint.
* The identity store (MongoDB) is backed up separately.
* Single instance: a deploy or crash means a short outage.
* Tokens last 7 days and there is no server-side revocation; rotate `JWT_SECRET` to invalidate all sessions.
